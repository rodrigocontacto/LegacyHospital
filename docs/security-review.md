# Security review - LegacyHospital

- **Date:** 2026-11-24
- **Scope:** `web/` (ASP pages, includes, `web.config`, `global.asa`), `db/` (T-SQL scripts), `.gitignore`, and the IIS Express configuration generated by Visual Studio (`.vs/LegacyHospital/config/applicationhost.config`).
- **Method:** manual code review. Database protections (SQL injection, IDOR, sort whitelist, permissions of `hospital_web`) were tested against a LocalDB copy. ASP pages were syntax-checked with `cscript` but **not yet run under IIS**.
- **Not reviewed:** `web/add_note.asp` (not in the repository yet).

Severity: **Medium / Low / Info**. None is High in the current local setup; findings that become High in production are marked.
**LC** = low confidence (see [Low-confidence notes](#low-confidence-notes)).

## Verification log

**2026-11-24 - first end-to-end run** (IIS Express 10 `/path:web /port:8080`, LocalDB, MSOLEDBSQL19; 38 scripted HTTP checks, all passing after the fixes below).

- **F-07 confirmed, then fixed.** Before the fix, `ASPSESSIONID` had the same value before and after login: ASP hides its session cookie from `Request.Cookies`, so `ExpireAspSessionCookies` never found it, and after `Session.Abandon` ASP reused the same ID. Fix: parse the raw `HTTP_COOKIE` header. Verified: the login POST now returns `Set-Cookie: ASPSESSIONID…=; Expires=1970…` and the ID changes (`DOLDMGBD…` → `FOLDMGBD…`).
- **F-19 closed** by the same fix: only names matching `ASPSESSIONID[A-Z]{8}` are written back.
- **F-20 closed:** `Cache-Control: no-store` observed on `login.asp` and `patient.asp`.
- **F-02 confirmed:** ASP sends `Set-Cookie: ASPSESSIONID…=…; path=/` with no `HttpOnly`, `Secure` or `SameSite`.
- **Functional bug fixed (not a security finding):** `report.asp` with the default sort failed because `ORDER BY [ScheduledAt], a.ScheduledAt` repeats a column. The generic error page was shown and the detail logged in `AppErrorLog`, as designed.
- **Observation:** requests blocked by request filtering (`/includes/…` 404.8, `/global.asa` 404.7, `/web.config` 404.8) end with a connection reset instead of a 404 body under IIS Express. The files are never served. To re-check under full IIS.
- Also verified over HTTP: generic login error, CSRF rejection, SQL injection / XSS / attribute breakout in `search.asp`, IDOR 404 with identical bodies, 400 for malformed IDs, sort whitelist 400 in `report.asp`, logout POST-only, security headers present, `Server` and `X-Powered-By` removed.

**2026-11-24 - layered refactor and new design.** `web/includes/db.asp` and `web/includes/security.asp` were split into `includes/core/*`, `includes/data/*` and `includes/views/*` (see CLAUDE.md, "Structure"). Locations in the table above refer to the pre-refactor files; mapping:

**2026-11-24 - F-01, F-02 and F-15 closed.**

- **F-01.** A test page with a runtime error (`1 / 0`) showed that `error.asp` already handled it as the 500.100 handler: generic page, status 500, and `Server.GetLastError()` logged file, line and message to `AppErrorLog` (this also resolves the earlier doubt about `GetLastError` under `ExecuteURL`). The second layer failed, though: with `error.asp` removed, ASP printed the VBScript error, file and line. Root cause: IIS Express in `/path` mode regenerates a temporary config from the template in `C:\Program Files\IIS Express` on every start, where `scriptErrorSentToBrowser="true"`, so editing the user config had no effect. Fix: `tools/run-local.ps1` now starts IIS Express with its own config (`/config` + `/site`, stored in `%LOCALAPPDATA%\LegacyHospital\iisexpress`) and sets `scriptErrorSentToBrowser="false"` there and in the Visual Studio config (`.vs`). Verified: without `error.asp`, the body is ASP's generic "An error occurred on the server when processing the URL", with no VBScript text, file or line. On full IIS, set it with `appcmd` (see `tools/run-local.ps1`).
- **F-02.** URL Rewrite outbound rules in `web.config` add `HttpOnly; SameSite=Lax` to the exact cookie ASP emits, and `Secure` under HTTPS. Verified on the first request and on login step 2, where the response carries two `Set-Cookie` headers (new ASP session + `LoginTicket` deletion): both keep their attributes. Three checks added to `tests/e2e-security.ps1`. Full IIS needs the URL Rewrite module installed.
- **F-15.** `app.usp_NoteReport_Get` dropped and `SELECT` on `PatientNotes` revoked from `app_dynamic_reader` (the script also cleans up existing databases). Verified with `sys.database_permissions`: only `Patients` and `Appointments` remain.
- **Found while verifying:** Visual Studio had added `<system.web><compilation debug="true"/>` to `web.config` (accepted when starting with F5). It is an ASP.NET setting with no effect on Classic ASP, but scanners report it as debug mode; removed, with a warning comment in `web.config`.
- `tests/e2e-security.ps1`: 42 checks, all passing.

**2026-11-24 - F-22 closed: `add_note.asp`.** GET shows the form, POST saves through `Notes_Add` (`app.usp_PatientNote_Add`) and redirects to the record (POST-redirect-GET). Controls: `RequireLogin`; `id` through `IsValidInteger` (400); patient loaded with `CurrentUserId()` before showing or saving, same 404 body as `patient.asp` for another doctor's patient; ownership checked again inside the procedure (insert-select); `ValidateCsrfToken` first in the POST; blank and >2000-character notes rejected in the browser, in ASP and in the procedure, with CRLF normalized to LF so the three limits agree; redirect built from a fixed path and the validated integer; note stored as plain text and displayed with `HtmlMultiline()`. Eleven checks added to `tests/e2e-security.ps1` (53 total, all passing), including "POST to another doctor's patient inserts no row" (verified in the database) and a stored `<img onerror>` payload shown encoded. Browser check: no console messages; screenshots `docs/screenshots/add-note.png` and `note-added.png`.

**2026-11-25 - all remaining findings closed.** Database changes were first tested from scratch on a separate LocalDB instance, then applied to the development database (upgrade path, re-runnable), which was finally rebuilt from scratch with `run-local.ps1 -RebuildDatabase`. `tests/e2e-security.ps1`: 73 checks, all passing.

- **F-03.** IIS Express binds HTTPS on 44300 (its trusted development certificate) and HTTP on 8080; a URL Rewrite rule in `web.config` answers every HTTP request with a 301 to the same URL over HTTPS (port map `HttpsPortSuffix`, empty in production = 443). `Strict-Transport-Security` on HTTPS (`max-age=300` on localhost, because HSTS covers every port of the host; one year elsewhere). `Secure` on `LoginTicket` and, through `<session keepSessionIdSecure="true">`, on `ASPSESSIONID`. **Found while verifying:** with `keepSessionIdSecure`, ASP emits `ASPSESSIONID…=…; secure; path=/`, which no longer matched the F-02 rewrite rule, so the session cookie lost `HttpOnly`. The rules now match both forms; the test checks `HttpOnly; SameSite=Lax; Secure`.
- **F-04.** `app.usp_User_Login` takes the client IP (`REMOTE_ADDR`, never `X-Forwarded-For`) and counts failed and blocked logins plus CSRF failures from that IP in the last 60 s in `SecurityAudit`; at 30 it returns 3 without checking the password and `login.asp` answers `429` with `Retry-After: 60`. An `sp_getapplock` per IP serializes sign-ins from one IP, so parallel requests cannot all read the count before any failure is written. Verified as `hospital_web`: attempt 30 → 1, attempt 31 (right password) → 3, another IP → 0; over HTTP the 429 arrives within 31 attempts and also refuses the right password.
- **F-05.** Iterations are versioned (`Users.HashVersion`, `dbo.ufn_Password_Iterations`): version 1 = 10,000 (~45 ms), version 2 = 60,000, **measured 149 ms per hash** (average of 5). Version-1 hashes are checked with their own count and replaced with a version-2 hash and a new salt on the next successful login (audit detail `PasswordRehashed`); for those users the new hash is computed on failure too, so timing is the same. Measured: existing user + wrong password 150 ms, unknown user 148 ms, right password 149 ms. Still SHA-512 (no bcrypt/Argon2 in SQL Server or VBScript): kept as a known limitation.
- **F-06.** `dbo.SecurityAudit` (time, event, outcome, user, typed username, IP, patient, detail). Written by `app.usp_User_Login` (every attempt, with the reason only the database sees: `BadPassword`, `UnknownUser`, `Inactive`, `AccountLockout`, `IpUserLockout`, `IpRateLimit`…) and by `app.usp_SecurityAudit_Add` from the pages: CSRF failures, record views and denied IDs (`patient.asp`, `add_note.asp`), notes added, sign-outs and ended sessions. `hospital_web` cannot read the table or call the internal writer (tested). Retention 6 years. Tests: one failed login → +1 row; one own record + two foreign/missing IDs → +1 Success and +2 Denied.
- **F-08.** `run-local.ps1` removes inherited permissions from `config\` and grants only the current user (the IIS Express identity), Administrators and SYSTEM (by SID, names are localized); files inside inherit exactly that. Checked with `icacls`. **Residual risk:** the `.udl` still holds a password, because IIS Express runs as the developer, who is sysadmin on LocalDB, so Windows authentication would not give a least-privilege identity. On full IIS: create a login for `IIS APPPOOL\<pool>` with the same rights as `hospital_web` and drop the password. `Trust Server Certificate=True` is only acceptable because LocalDB is local; validate the certificate for any remote server. Procedures still trust the `@UserId` the app sends: anyone holding the `hospital_web` credentials can read every patient.
- **F-09.** `git ls-files .vs config` returns nothing; `git check-ignore` matches `config/hospital.udl`, `config/password.txt` and `.vs/…/applicationhost.config`.
- **F-10.** Both IIS Express configs (run-local and `.vs`) point to `web\`; `run-local.ps1` now enforces it for the `.vs` one too. `/config/hospital.udl`, `/db/01_schema.sql` and `/CLAUDE.md` return 404 (tests).
- **F-11.** Search is a POST with CSRF token; the term is kept in the session and the POST redirects to `/search.asp` (POST-redirect-GET), so Back and reload work and the term never appears in a URL. A `q` in the query string is ignored. Tests check the form, the CSRF rejection, the `Location` and that `?q=` returns nothing. The local IIS Express config has W3C logging disabled, so the "not in the log" criterion was checked by construction: W3C logs only hold the path and query string, never a POST body.
- **F-12.** `Session("LoginAt")` with an absolute limit of 8 h, and `app.usp_User_IsActive` re-read every 5 minutes in `RequireLogin()`; an ended session is signed out, audited (`Session/Blocked`, `AbsoluteTimeout` or `UserInactive`) and sent to `login.asp?ended=1`. Verified over HTTP with the two constants temporarily set to 1 and 0 minutes (then restored): deactivating dr.chen sends the next request to the login page and the old session cookie is no longer accepted; a session 65 s old is ended although it was used 65 s earlier.
- **F-13.** The per-account lockout became a safety net (50 consecutive failures → 15 minutes); the main lockout is per IP + username (5 failed passwords in 15 minutes since the last success from that IP). Tested: after 5 failures from one IP the right password is refused there and accepted from another IP; over HTTP dr.garcia still signs in from the IP where dr.smith is locked. **Residual risk:** locking a doctor out now needs 50 failures from at least 10 IPs.
- **F-14.** CSRF failures go to `SecurityAudit` instead of `AppErrorLog` and count toward the F-04 limit; non-success audit rows are capped at 100 per IP per minute; `AppErrorLog` accepts at most 100 rows per minute and purges rows older than 90 days. - **F-18.** `cmd.NamedParameters = True` in `CreateSpCommand` and `LogError`. - **F-21.** `Option Explicit` is the first statement of `global.asa`; `tests/asp-syntax-check.ps1` now fails if it is missing. The application restarted with it (every page works, sessions start).

## Low-confidence notes

- **F-07:** the mitigation depends on two things not verified without running the app: the browser deleting `ASPSESSIONID` when told to, and ASP not reusing the same ID. If both hold, there is no vulnerability.
- **F-10:** by default IIS refuses to serve extensions without a registered MIME type (`.udl`, `.sql`, `.md` return 404.3), so exposing the repository root probably does not serve those files. Kept as a configuration risk, not a confirmed exposure.
- **F-19:** ASP splits cookies on `;` and `=`, so a name cannot carry new attributes, and the request comes from the victim's own browser. No exploit found; kept as hardening.
- **F-20:** ASP's handling of a non-standard `Response.CacheControl` value is unverified. Check the real header.

## What is done well

No findings for SQL injection, XSS, IDOR, CSRF or user enumeration. These protections were tested in the database; the pages were only syntax-checked.

- **SQL injection:** every value is a parameter, including inside the dynamic ORDER BY. Sort columns go through a whitelist in ASP and again in SQL, then `QUOTENAME`; dynamic SQL runs as `app_dynamic_reader` (SELECT only).
- **XSS:** every output goes through `Html()`. A CSP without inline scripts is a second barrier.
- **IDOR:** the `@UserId` filter is part of the query itself; "does not exist" and "not yours" return the same 404.
- **CSRF:** tokens on every POST, including login and logout; constant-time comparison.
- **User enumeration:** one generic login message; the hash is computed even for unknown users so timing is similar.

## Re-running the review

Authenticated OWASP ZAP scan (development database only; exclude `login.asp` and `logout.asp` from the context to avoid lockouts and log flooding; add `csrf_token` under *Options → Anti-CSRF Tokens*). Save reports in this folder as `zap-authenticated-YYYY-MM-DD.html`.

Expected ZAP results:
- "Cookie No HttpOnly Flag" / "Cookie without SameSite Attribute" / "Cookie Without Secure Flag" on any cookie would contradict F-02/F-03 and must be investigated.
- "Absence of Anti-CSRF Tokens" on the `report.asp` form is a false positive (read-only GET).
- The scan triggers the login rate limit (F-04) if `login.asp` is not excluded: expect 429 responses.
- Any SQL Injection or Cross Site Scripting alert with Medium/High confidence contradicts the database tests and must be investigated.

To close a finding: apply the fix, check its acceptance criteria, change **Status** to `Closed (YYYY-MM-DD)` and note how it was verified.
